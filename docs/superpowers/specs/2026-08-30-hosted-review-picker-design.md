# Hosted Review Picker — Design

**Date:** 2026-08-30
**Status:** approved, ready for implementation planning
**Context:** `formatting-scripts/review_page.py`, `formatting-scripts/apply_picks.py`, `catalogue-batches/review-pickers-index.html`

## Purpose

Today's `review-picker.html` pages are self-contained static files that only work locally: picks are saved to the browser's `localStorage`, and a manual "Export picks" button downloads a `tmdb-picks.json` file that has to be moved into the right `out-*/` folder by hand before `apply_picks.py` can run.

The client is not local — he needs a URL he can open and click through, with no file-juggling on his end. This design hosts the picker publicly and replaces the local-file handoff with picks committed directly into the repo, so the workflow stays "git pull, then run `apply_picks.py`" for the operator (Liam), with no manual export/import step and no database.

## Scope

**In:** hosting the existing picker UI (candidate cards, hide-decided, TMDB/Google lookup links) at a public URL; replacing manual JSON export with an auto-save that commits picks straight to the repo; a batch index page with live progress; light UI friendliness improvements now that the "Export" button goes away.

**Out, deliberately:**
- Any database. Git is the only datastore — a JSON file per batch, committed by a serverless function.
- Login/auth. The URL is unlisted; nothing more secure is needed for one known client.
- Concurrent-editor conflict resolution beyond a single retry. One client works through one batch at a time; this is not built for multiple simultaneous editors.
- Any change to `apply_picks.py`'s input contract — it keeps reading the same array-of-picks JSON shape it reads today, just from a committed file instead of a downloaded one.

## Operating context

| | |
|---|---|
| **Hosting** | Vercel, connected to `paris-liam/LMS`, auto-deploy on push |
| **Location in repo** | `tools/review-picker/` (matches the existing `tools/movie-uploader/` convention) |
| **Who operates the picker UI** | The client, unaided |
| **Who operates the generate/apply scripts** | Liam, from this local checkout |
| **Access control** | Unlisted URL only, no login |
| **Save mechanism** | One Vercel serverless function, GitHub Contents API, no DB |

## Architecture

```
tools/review-picker/
  public/
    index.html              # batch launcher + live progress
    <batch>/index.html       # one page per batch, generated
  api/
    save-pick.js            # Vercel serverless function (Node) — write
    get-picks.js            # Vercel serverless function (Node) — read
  data/
    <batch>.json             # committed picks, one file per batch
```

- **Static pages** are generated by a Python script (adapted from `review_page.py`) the same way as today: TMDB candidates fetched once, embedded into the page as JSON. Liam runs this after `run.py` produces a batch's `review-picker.html`-equivalent data, then commits and pushes — Vercel auto-deploys.
- **`/api/save-pick`** is the write path. It receives one pick, reads `data/<batch>.json` via GitHub's Contents API (`GET .../contents/tools/review-picker/data/<batch>.json`), merges the new entry in (insert or replace by `handle`), and writes it back (`PUT` with the previous `sha`).
- **`/api/get-picks`** is the read path, used both by a picker page on load (to restore already-decided cards) and by the index page (to compute live progress). It proxies the same GitHub Contents API read. Routing reads through a function rather than fetching `raw.githubusercontent.com` directly from the browser means this works the same way whether or not `paris-liam/LMS` is public, and the GitHub token is never exposed to the browser.
- Both functions authenticate to GitHub with a single fine-grained PAT, scoped to only this repo with Contents:read/write, stored as a Vercel environment variable.
- Each save is its own commit. This is a feature, not a cost: it gives a free, ordered audit trail of the client's decisions with no extra logging code.

## Data flow

1. Liam runs `run.py` on a batch, then the adapted generator to produce `tools/review-picker/public/<batch>/index.html` and an empty `data/<batch>.json`. Commit and push.
2. Vercel deploys; Liam sends the client `https://<project>.vercel.app/<batch>/`.
3. On load, the page calls `/api/get-picks?batch=<batch>` to fetch the *current* committed picks and restore already-decided cards. This makes the page correct from any device/browser, unlike today's `localStorage`-only state.
4. Client picks a candidate → page immediately `POST`s `{batch, handle, choice, poster_path/overview or image_src/overview, ...}` (same shape as today's exported pick objects) to `/api/save-pick`. Card shows **Saving… → Saved ✓**.
5. `localStorage` is kept only as a same-device fallback cache: if a save fails, the pick is held there and retried (in the background, or on the next interaction), and the card shows **Not saved — retrying**. No pick is silently dropped.
6. Whenever Liam checks in: `git pull`, then `python3 formatting-scripts/apply_picks.py data/<batch>.json out-<batch>/upload.csv` exactly as today — no format change needed.

## Error handling

- **Save request fails** (network blip, GitHub rate limit): function returns non-2xx, client keeps the pick queued in `localStorage`, shows a retry state, and retries automatically.
- **Stale `sha`** (the file changed between the function's read and write — the realistic case is the client picking two products in quick succession before the first commit lands): the function re-fetches the current file and `sha` and retries the merge once before surfacing an error to the client.
- **Malformed batch name / unknown handle**: function validates `batch` against a fixed allow-list check (file must already exist at `data/<batch>.json`) and rejects unknown batches with a 400, so a stray request can't create arbitrary files in the repo.

## UI improvements

The "Export picks" button and its file-based mental model go away, replaced by a per-card save-state indicator. While touching the page, also:
- Add a one-line plain-language header explaining the task ("Pick the right poster and description for each movie — your choices save automatically as you go").
- De-emphasize "Manual entry" and "Skip" as smaller secondary links rather than equal-weight radio options next to the real candidates.
- Larger touch targets on candidate cards.
- Keep the progress counter and "Hide decided" toggle — they already work well.
- The batch index page's progress bars read from `/api/get-picks` (the same read path used for page hydration) instead of `localStorage`, so Liam can check progress remotely without touching the client's browser.

## Testing

No automated suite fits a static page plus one function. Verification is manual: deploy to a Vercel preview, click through a handful of picks across a couple of batches, confirm each produces the expected commit/diff in GitHub, confirm a stale-`sha` retry actually recovers (simulate by firing two rapid picks), and confirm `apply_picks.py` runs unchanged against the resulting `data/<batch>.json`.
